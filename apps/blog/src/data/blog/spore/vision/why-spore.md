这是一篇面向系列开头的写作大纲。它不急着讲语法和实现，而是先回答一个更根本的问题：**为什么还需要一门新的语言，Spore 想重新组织的到底是什么。**

文章的目标不是宣称 “Spore 什么都更好”，而是把它瞄准的那类长期分裂问题讲清楚：函数签名、外部世界边界、可执行契约、未完成代码与工具消费，为什么值得被放进同一个设计故事。

## 写作目标

- 让读者先理解 Spore 的问题意识，而不是先看到一堆 feature。
- 给后续整组文章建立总命题：**函数签名是重力中心**。
- 说明 Spore 优化的不是“更炫的语法”，而是**重新组织语言契约**。

## 核心论点

- 现代语言里，**类型、effect、成本、测试、未完成代码**通常分散在不同地方，导致语言契约被拆碎。
- Spore 试图把这些信息重新收拢到函数签名及其周边协议里。
- Spore 的真正差异，不在于单个机制，而在于这些机制被设计成一个系统。
- Spore 不是通用地追求“最强保证”，而是追求**可解释、可落地、对开发者和 Agent 都友好的强保证**。

## 建议结构

### 引子

- 从你长期观察到的问题切入：很多语言把“参数和返回值”当作函数签名的全部，但真正重要的信息远不止这些。
- 给一个直觉例子：同一个函数，类型正确，不代表 effect 正确；effect 正确，不代表成本可信；测试存在，也不代表契约清晰。

### 问题到底出在哪里

- 类型与行为契约分离：测试和文档在函数外，签名里只剩最薄的一层信息。
- 外部世界边界模糊：IO 直接进 stdlib，测试、沙箱、替换运行时都困难。
- 未完成代码处理粗糙：`TODO`、`panic`、注释无法给工具提供结构化上下文。
- 编译器、IDE、Agent 各自消费一份不同的“事实版本”。

### Spore 的总回应

- 把函数签名扩成 `type + effect + cost + spec`。
- 把 IO 收束到 `Platform` 边界，而不是散落在语言核心和标准库内部。
- 把 `hole` 提升成一等协议，而不是临时占位。
- 把机器可消费输出视为主设计目标，而不是附属功能。

### Spore 优化什么，不优化什么

- 优化：
  - 可组合的函数契约
  - 可验证的边界
  - 对 Agent 友好的结构化语义
  - 对工具链友好的 machine projection
- 不优化：
  - 把一切证明到 theorem prover 等级
  - 把 ownership / lifetime 变成用户默认心智
  - 用 rich direct FFI 换掉 capability / Platform 边界

### 用一句话收束

- 给出一句尽量稳定的定义，例如：
  - **Spore 是一门以函数签名为中心、以 Platform 隔离外部世界、以 spec 驱动验证的语言。**

## 写作边界

- 不展开具体语法细节。
- 不进入实现顺序。
- 不详细比较具体语言优劣，只拿它们做背景参照。
